# Quality and security

Quality does not rely on the agent's goodwill: it is enforced at three levels, later and later in the
cycle.

| Level | When | Tool |
|---|---|---|
| Before each action | on every command, write or read by Claude | `guardrails` hooks |
| During the work | on every file touched, on every review | per-language rules, `ponytail`, review skills |
| Before each merge | on every PR | CI generated by `ci-forge`, required check `ci-ok` |

## Guardrails (`guardrails`)

A single hook, written in Node, examines every command, write and read by Claude before it runs.

| Rule | Default | What is refused |
|---|---|---|
| `em-dash` | blocks | em dash added in a file, a commit, a PR, an issue, a text written by a command; lines staged at commit |
| `emoji` | blocks | unrequested emoji (the AI marker and the attribution line remain allowed; per-path exceptions) |
| `protected-push` | blocks | push to `main` or `master`, including from the current branch, via `HEAD`, after a checkout in the same command, deletion, `--all`, `--mirror` |
| `no-verify` | blocks | `--no-verify`, `commit -n`, `core.hooksPath`, `HUSKY=0` and equivalents |
| `secrets` | blocks | known keys and tokens, plaintext password, in a file, a command or the staged lines (`.env` files exempted) |
| `env-file` | blocks | `git add` or commit of a `.env` file |
| `conventional-commit` | blocks | message not in Conventional Commits format, first line longer than 72 characters |
| `ai-marker` | blocks | PR or issue title written by the AI without the marker |
| `prod-credentials` | blocks | Kubernetes secrets, vaults, shell history, another project's `.env`, tunnel to production |
| `lint-config` | warns | lint configuration modified, warning suppression added |
| `config-tamper` | asks | any change to the guardrails configuration or their removal |

Each refusal gives the rule, the reason and the fix. Rules are tuned or turned off in
`.claude/guardrails.json` (project) or `~/.claude/guardrails.json` (machine). A copy installed in the
project (`setup.cjs install-project`) serves the team and cloud sessions; the plugin's copy then stays
silent. An internal error lets the action through rather than blocking the work. The engine is covered
by 42 end-to-end tests and has been verified in a real Claude Code session.

The same rules protect the other coding agents: `setup.cjs install-project --harness codex,gemini,cursor`
(or `all`) wires the project copy in each agent's hook file, and the universal installer does it at user
scope. Each agent's tool calls (shell, file writes, edits, Codex `apply_patch`) are translated into the
calls the rules know, and the answer uses that agent's protocol. See [Coding agents](harnesses.md).

## Generated CI/CD (`ci-forge`)

`detect_stack.py` reads the repository's manifests; the skill derives a CI per level from them:

- **PR**: format, lint, type checking, tests with ratcheted coverage, build, secret scanning, dependency
  audit, workflow checks, and depending on the files touched, container and Kubernetes manifests;
- **main branch**: in addition, full end to end, trial deployment on an ephemeral cluster, SBOM,
  published image, staging;
- **nightly**: full matrix, mutation tests, load and Lighthouse on staging, dynamic security audit;
- **release**: artifacts, provenance, signing, production.

Actions are pinned by SHA (`pin_actions.py`, from the published tags), permissions are minimal, commands
come from a single task runner so that local and CI give the same result, and `actionlint` and `zizmor`
validate the workflows. All commands are run locally before the PR (in an official container if a tool
is missing): a real trial showed that a CI never run can fail on a file it generated itself.

## Reviews

| Skill | What it requires |
|---|---|
| `security-review` | evidence for each finding (file, line, path from source to sink), a confidence level, a severity, a search for variants, a minimal tested fix, a list of design footguns |
| `sast` | Semgrep and CodeQL locally, triage of each result as true positive, justified false positive or lead |
| `ui-review` | the interface rendered on desktop and mobile, measured accessibility, states, forms, perceived performance |
| `ponytail-review` | correctness, safety, behavior under load, tests, and the usefulness of each line |
| `gate-verifier` | a fixed loop (build, type checking, lint, tests, dependencies, secrets, diff) rendered as a table; a check that was not run is never counted as passed |

## Per-language rules

Eleven short rules (Python, TypeScript, React and Next.js, Go, Rust, shell, SQL, Docker, Terraform,
Kubernetes, tests), written in `.claude/rules/ultime/` by `ultime-profile`. Each carries a `paths:` field
and is only loaded when Claude reads or modifies a matching file.

## Ponytail everywhere

`ponytail` injects into every session and every subagent the smallest-complete-change rule: reuse before
writing, add nothing that does not serve the task, explain in a single read. It weighs about 2,900
characters per session.
